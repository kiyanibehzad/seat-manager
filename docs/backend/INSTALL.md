# نصب و راه‌اندازی اولیه

این راهنما روش نصب خام برنامه روی PHP و MySQL/MariaDB را توضیح می‌دهد. سازگاری PHP، مسیرهای خصوصی، HTTPS، ارسال ایمیل و زمان‌بندی باید روی هاست مقصد بررسی شوند؛ نصب اولیه به‌تنهایی تأیید همهٔ امکانات عملیاتی هاست نیست.

## نیاز مقصد

PHP 8.3+، PDO MySQL، OpenSSL، mbstring، session، ctype/filter/hash/json و MySQL 8.0+ یا MariaDB 10.6+ با InnoDB و utf8mb4. برای ایمیل و یادآوری، اجرای کوتاه PHP CLI از cron لازم است. زمان‌های پایگاه داده UTC و نمایش برنامه به وقت ایران است. Node، Docker، Redis و Composer روی هاست لازم نیستند؛ وابستگی PHP و فایل‌های ساخته‌شدهٔ رابط همراه بسته‌اند. SSH روش اجباری نصب نیست؛ کنترل‌پنل و file manager با دسترسی لازم نیز کافی‌اند.

## ساخت بستهٔ کامل

برای نصب روی هاست، بستهٔ آمادهٔ `seat-manager-v0.1.0-beta.2.zip` را از [GitHub Releases](https://github.com/kiyanibehzad/seat-manager/releases/tag/v0.1.0-beta.2) دریافت کنید. این بسته رابط ساخته‌شده، وابستگی‌های PHP و سه وزن فونت وزیرمتن را دارد؛ نیازی به اجرای فرمان‌های ساخت زیر روی هاست نیست. فونت از خود برنامه بارگذاری می‌شود و روی دستگاه کاربران نیاز به نصب ندارد. فایل `SHA256SUMS.txt` کنار بسته برای بررسی دانلود و `MANIFEST.release.json` داخل آن برای بررسی فایل‌هاست. آرشیوهای خودکار «Source code» شامل وابستگی‌های آماده نیستند.

روی محیط توسعه، وابستگی‌ها و رابط را آماده کنید و سپس بسته بسازید:

```sh
composer install --working-dir=backend --no-dev --prefer-dist
node frontend/build.mjs
php bin/build-release.php /absolute/private/output/seat-manager-release.zip
```

بستهٔ کامل شامل backend و vendor آماده، API، index.html، install.html، assets، migrationها و config/app.example.php است. هیچ تنظیم خصوصی، app_key، کلید نصب، DB، کاربر، نشست، ایمیل یا لاگ توسعه وارد آن نمی‌شود. خروجی archive باید بیرون public_html نگهداری شود. فایل‌های مجوز وابستگی‌ها حفظ شوند؛ استفاده از فونت اختیاری محلی تابع مجوز همان فونت است.

برای انتشار عمومی، رابط را با `node frontend/build.mjs --public` و بسته را با `php bin/build-release.php --public /absolute/private/output/seat-manager-public.zip` بسازید. این حالت همیشه وزیرمتن داخلی و مجوز آن را همراه می‌کند و فونت خصوصی یا ناشناخته را نمی‌پذیرد. نسخهٔ عادی بدون این گزینه، فونت شخصی دارای مجوز را در صورت موجود بودن برای استقرار همان مالک حفظ می‌کند.

نام قدیمی `bin/build-package.php` فقط برای سازگاری فرمان‌ها باقی است و به همان سازندهٔ بستهٔ کامل `build-release.php` هدایت می‌شود؛ دیگر بستهٔ جداگانهٔ backend یا کلید و تنظیم آمادهٔ نصب تولید نمی‌کند. رابط و وابستگی‌ها باید از قبل آماده باشند؛ گزینهٔ `--public` و ممنوعیت خروجی در `public_html` برای هر دو فرمان یکسان‌اند. بررسی‌گر قدیمی `tests/backend/package.php` نیز فقط به بررسی‌گر خواندنی `release-package.php` هدایت می‌شود و نصب، دسترسی به تنظیم خصوصی، اتصال دیتابیس یا ارسال ایمیل انجام نمی‌دهد.

## ساختار خصوصی و عمومی

```
seat-manager/                   # خارج از ریشهٔ وب
  backend/ config/ database/ storage/ bin/ docs/
  public_html/                  # تنها ریشهٔ قابل دسترس وب
    index.html
    install.html
    assets/
    api/index.php
    api/install.php
```

document root دامنه را public_html قرار دهید. backend، config، database، storage، bin و آرشیوهای نصب نباید از وب قابل دریافت باشند. اگر کنترل‌پنل ساختار دیگری تحمیل می‌کند، مسیر require در هر دو ورودی API را برای هر دو فایل خصوصی backend/src/SecurityHeaders.php و backend/bootstrap.php هماهنگ کنید. در ارتقا ابتدا helperهای backend را مستقر کنید و سپس ورودی‌های API را جایگزین کنید. برای نصب در زیرپوشه نیز فقط فایل‌های عمومی را نگاشت کنید؛ app_url ریشهٔ واقعی نصب، مانند https://company.example/team، باشد تا مسیر cookie و لینک‌ها درست ساخته شوند. مخفی‌کردن فایل خصوصی با نام یا پسوند جای document root درست را نمی‌گیرد.

فایل .htaccess همراه بسته را نیز منتقل کنید؛ بعضی file managerها فایل‌های نقطه‌دار را مخفی می‌کنند. هدرهای محافظتی صفحات اصلی، نصب و API و HSTS فقط روی HTTPS باید در پاسخ واقعی بررسی شوند. اگر Nginx یا پروکسی صفحه‌های HTML را مستقیم می‌فرستد، معادل هدرها را در تنظیم دامنه اعمال کنید؛ [راهنمای هدرهای امنیتی](SECURITY-HEADERS.md) جزئیات را دارد.

storage برای کاربر اجرای PHP قابل نوشتن باشد؛ معمولاً پوشه‌های خصوصی 700/750 و فایل‌ها 600/640 مطابق مدل مالکیت هاست. backend و config برای اجرای معمول وب نیاز به دسترسی نوشتن ندارند. فایل‌های عمومی باید برای وب‌سرور خواندنی باشند.

## آماده‌سازی تنظیمات مقصد

1. در کنترل‌پنل یک DB و کاربر اختصاصی بسازید. دسترسی همان DB باید ساخت جدول و اجرای migrationهای اولیه را هم اجازه دهد.
2. به‌صورت خصوصی config/local.php را از config/app.example.php بسازید. app_url واقعی HTTPS، DSN و نام/رمز DB، environment=production و session.secure=true را تنظیم کنید.
3. app_key تازه با ۳۲ بایت تصادفی امن تولید و به صورت base64 ذخیره کنید. کلید نصب جداگانه و پُرآنتروپی بسازید؛ فقط SHA-256 آن را در setup.token_hash قرار دهید و setup.enabled=true کنید. اصل کلید نصب را خصوصی و خارج از ریشهٔ وب نگه دارید. app_key یا کلید نصب در Git، URL، گزارش یا لاگ چاپ نشوند.
4. برای ورود اولیه می‌توان smtp.enabled=false را نگه داشت. تنظیمات واقعی ایمیل بعداً، پیش از اتکا به دعوت کارکنان، تأیید ایمیل، بازیابی رمز و یادآوری ایمیلی، آماده و آزموده شوند. در محیط production از tls یا ssl با بررسی معتبر گواهی استفاده کنید.

app_key را با پشتیبان خصوصی DB و تنظیمات نگه دارید؛ تعویض آن پیام‌های رمزگذاری‌شدهٔ موجود در صف را ناخوانا می‌کند. تنظیمات و storage یک نصب موجود را با فایل‌های بستهٔ تازه جایگزین نکنید.

## اولین ورود: ساخت مدیر کل

آدرس **/install.html** را با HTTPS باز کنید. فرم این موارد را می‌گیرد:

- کلید نصب یک‌بارمصرف خصوصی؛
- ایمیل، نام و نام خانوادگی اولین مدیر کل؛
- نام بخش اولیه؛
- رمز انتخابی مدیر کل و تکرار همان رمز.

**نام کاربری یا رمز ثابت و پیش‌فرض وجود ندارد.** ایمیل واردشده شناسهٔ ورود است؛ رمز را شخص ایجادکنندهٔ حساب انتخاب می‌کند. حداقل رمز ۱۲ نویسهٔ Unicode و سقف آن ۷۲ بایت UTF-8 است. اولین مدیر بلافاصله فعال و عضو گروه محافظت‌شدهٔ مدیر کل می‌شود؛ ورود اولیه منتظر ایمیل نمی‌ماند. رمز انتخابی نه ایمیل می‌شود و نه در پاسخ نصب نمایش داده می‌شود.

فرم وضعیت را از GET api/install.php می‌گیرد؛ این خواندن قبل از ساخت schema نیز ممکن است و migration اجرا نمی‌کند. ثبت با POST JSON، هدر X-Install-Token و CSRF نشست در X-CSRF-Token روی همان origin انجام می‌شود. کلید نصب و CSRF در query/fragment آدرس، localStorage یا دادهٔ ماندگار رابط قرار نمی‌گیرند. تلاش‌های نصب پیش از آماده‌شدن schema نیز در فایل خصوصی محدود می‌شوند: حداکثر ۲۰ تلاش در ۱۵ دقیقه برای هر IP.

نصب اولیه migrationهای لازم را اجرا می‌کند؛ import دستی SQL لازم نیست. حساب OpenAI، سیت یا کاربر آزمایشی ساخته نمی‌شود. فقط مدیر کل، بخش اولیه، دامنهٔ ایمیل همان مدیر و گروه‌های پایه ایجاد می‌شوند. دامنه‌های مجاز و اطلاعات واقعی شرکت پس از ورود قابل تکمیل‌اند.

پس از موفقیت، با همان ایمیل و رمز انتخابی وارد شوید. فرم نصب بسته می‌شود؛ وجود اولین کاربر هم پیش از migration و هم دوباره زیر قفل تراکنش بررسی می‌شود تا نصب تکراری یا هم‌زمان حساب دیگری نسازد. کلید نصب باقی‌مانده نیز نمی‌تواند migration بعدی را از این مسیر اجرا کند. بعد از تأیید ورود، می‌توانید setup.enabled=false، token_hash خالی و اصل کلید نصب خصوصی را حذف کنید. این پاک‌سازی اضافی جایگزین قفل یک‌بارمصرف خود برنامه نیست.

روش قدیمی POST JSON بدون password/password_confirm فقط با تنظیمات رمزنگاری‌شده و از پیش فعال‌شدهٔ ارسال کار می‌کند. migration 004 ارسال خودکار را در شروع خاموش می‌گذارد؛ بنابراین در نصب تازه، رمز انتخابی و تکرار آن الزامی است و مسیر قدیمی نمی‌تواند حسابی با رمز دسترس‌ناپذیر بسازد.

## ایمیل و یادآوری پس از نصب

مدیر کل در تنظیمات، بخش ایمیل، یکی از SMTP یا PHP mail و فرستندهٔ واقعی را انتخاب می‌کند. رمز SMTP به‌صورت رمزنگاری‌شده در DB خصوصی ذخیره می‌شود؛ رمز خالی یعنی حفظ رمز قبلی و گزینهٔ پاک‌کردن یعنی حذف صریح آن. ابتدا اتصال را بررسی و تنها با دکمهٔ ارسال آزمایشی به گیرندهٔ مشخص پیام بفرستید. آزمایش صریح هنگام خاموش بودن ارسال خودکار نیز مجاز است. موفقیت PHP mail فقط پذیرش توسط سیستم ایمیل هاست است؛ دریافت در inbox، SPF/DKIM/DMARC و پوشهٔ spam را جدا بررسی کنید. پس از تعیین روش و فرستنده، ارسال خودکار را آگاهانه فعال کنید. تا آن زمان پیام‌ها در صف می‌مانند و لینک‌های منقضی ارسال نمی‌شوند. [راهنمای ایمیل و وضعیت صف](MAIL.md) و [قرارداد رابط](API-MAIL.md) جزئیات را دارند. تا پیش از این بررسی، کارکرد ورود اولیه نشانهٔ آماده‌بودن ایمیل نیست. از کنترل‌پنل، cron هر دقیقه با نسخهٔ سازگار PHP CLI و مسیر خصوصی زیر اجرا شود:

```sh
/path/to/php /private/seat-manager/bin/cron.php
```

تازگی موفق cron در پنل مدیر کل نمایش داده می‌شود؛ سبز بودن آن فقط شاهد اجرای موفق در پنج دقیقهٔ اخیر است. با خاموش بودن ایمیل، cron همچنان اعلان و یادآوری داخل برنامه را آماده می‌کند.

هر اجرا حداکثر ۲۰ پیام و بودجهٔ حدود ۴۰ ثانیه برای صف دارد؛ ارسال شروع‌شده ممکن است تا timeout خودش ادامه یابد. محدودیت و مسیر دقیق cron به هاست بستگی دارد. worker از مسیر عمومی وب اجرا نمی‌شود. انقضا هیچ سیتی را خودکار پس نمی‌گیرد؛ اقدام واقعی در OpenAI و ثبت نتیجه همچنان دستی است.

## ارتقا و گروه‌های دسترسی

برای نصب موجود، ابتدا در یک بازهٔ کوتاه نگهداری، نوشتن برنامه و worker/cron را متوقف کنید. یک snapshot خصوصی و هماهنگ از **DB کامل، config/local.php و app_key، کد backend/API و تمام assetهای رابط همان نسخه** بگیرید؛ خوانایی و کامل بودن پشتیبان را بررسی کنید. سپس کد و migration را هماهنگ اعمال کنید. DDL در MySQL/MariaDB کاملاً تراکنشی نیست. فایل SQL اعمال‌شده با checksum ثابت نباید ویرایش شود؛ نسخهٔ بعد باید migration تازه داشته باشد.

```sh
ACC_CONFIG=/absolute/private/config-for-selected-target.php php /private/seat-manager/bin/migrate.php
```

در صورت شکست و نیاز به بازگشت، برنامه و cron را متوقف نگه دارید و **همان مجموعهٔ هماهنگ DB + config/app_key + کد/API + assetها** را با هم بازیابی کنید؛ کد قدیمی را روی DB نیمه‌مهاجرت‌یافته رها نکنید. بازگردانی DB تمام نوشتن‌های پس از snapshot را هم برمی‌گرداند؛ زمان توقف و پشتیبان باید به همین دلیل هماهنگ باشند. rollback تراکنشی، DDL را به عقب برنمی‌گرداند و migration معکوسِ تخمینی اجرا نمی‌شود. پس از بازیابی، health، ورود، وضعیت صف و خاموش/روشن بودن ارسال را بررسی و فقط پس از موفقیت، نوشتن و cron را از سر بگیرید.

نصاب بسته‌شده مسیر ارتقا نیست. migration 004 جدول تنظیمات رمزنگاری‌شدهٔ ایمیل و وضعیت سرویس را افزایشی اضافه می‌کند، دادهٔ کاربران و صف را حفظ می‌کند و ارسال خودکار را خاموش می‌گذارد؛ مدیر کل آن را پس از تعیین روش و فرستنده فعال می‌کند. migration 003 گروه‌ها و عضویت کاربران را افزایشی اضافه می‌کند، بخش/امتیاز و حساب/سیت/سوابق را حفظ می‌کند و نشست‌های قدیمی را برای ورود دوباره منقضی می‌کند. user شخصی‌فقط و محافظت‌شده و admin مدیر کل محافظت‌شده است؛ HR/operator و گروه سفارشی قابل ویرایش‌اند. [قرارداد گروه‌ها](ACCESS-GROUPS-CONTRACT.md) مرجع قابلیت‌هاست.

## اجرای محلی و آزمون

راهنمای کامل محیط توسعه و آزمون در [SETUP.md](../SETUP.md) است. راه‌انداز `python3 bin/dev-services.py start|status|stop` فقط سرویس‌های محلی پروژه را اداره می‌کند؛ start migrationهای موجود را هم اجرا می‌کند. محیط development/test فقط به SMTP sink محلی می‌فرستد و relay بیرونی ندارد.

اطلاعات مدیر آزمایشی محلی فقط در فایل خصوصی storage/dev-access.txt است و وارد بستهٔ انتشار نمی‌شود. این اطلاعات در مستندات، چت یا لاگ کپی نشوند. suiteهای قدیمی backend پایگاه آزمون را بازسازی می‌کنند؛ فقط روی DB موقت و مجزا اجرا شوند. آزمون `tests/backend/first-install.php` پایگاه و HTTP موقت خودش را برای فرم نصب، رمز انتخابی، CSRF، نصب یک‌بارمصرف و سازگاری روش قبلی می‌سازد و سپس پایگاه موقت خودش را حذف می‌کند.
